<RichText id="recommendation">

## Recommendation

Build **Opssemble** around one continuous flow: **Change -> Watch Plan -> Release Mission**.

The **Changes** screen is the pre-merge control surface. It imports pull requests from a connected GitHub repository, scores their operational risk, proposes the agents and signals that should watch them, and lets a developer add requirements in plain language. Opssemble compiles that input into a structured Watch Plan that the developer can inspect and arm.

After merge, candidate deployment, or feature-flag dial-up, the armed plan becomes a durable **Release Mission**. The mission screen answers **what the agents are doing, what evidence they found, and what policy permits next**. Chat remains a secondary investigation surface. Promote, rollback, feature-flag restoration, and repair remain explicit commands with policy and human approval.

The hackathon MVP should prove one complete path:

1. A connected GitHub PR appears with an automatically proposed Watch Plan.
2. The developer adds "monitor EU checkout completion and duplicate Stripe attempts" and arms the plan.
3. Merge plus Vercel candidate readiness triggers a Release Mission.
4. Resilience, Performance, and Product Health agents evaluate the candidate.
5. Deterministic policy rejects the candidate; Codex receives a bounded repair task and the same contract reruns to green.

</RichText>

<Callout id="product-decision" tone="decision">

The product has two durable objects. A **Release Contract** stores operational intent before anything ships; a **Release Mission** is one execution of that contract after a merge, deployment, or feature-flag trigger. One PR can therefore produce multiple missions over its lifetime.

</Callout>

<RichText id="problem-statement">

## Problem Statement

Coding agents can now take a ticket through implementation, tests, and a mergeable PR. But operational intent is rarely captured before that PR ships. Teams do not have one place to state which customer journeys, dependencies, technical signals, and business outcomes must remain healthy as the change moves through deployment and exposure.

After merge, the remaining work fragments across deployment systems, observability, chaos tools, product analytics, security scanners, incident response, and backlog management. No existing surface owns the complete question: **what must we watch for this change, and did it remain safe as it moved through real deployment stages and customer exposure?**

Teams need a system that is:

- **Change-centric:** every conclusion is attached to the PR, deployment, release SHA, or flag rollout that caused it.
- **Intent-aware:** every monitored signal and action traces back to an inferred policy, repository rule, or explicit developer requirement.
- **Evidence-first:** agent claims resolve to measurements, traces, logs, screenshots, tests, or external records.
- **Policy-controlled:** models propose; deterministic policy and human approvals authorize.
- **Lifecycle-complete:** the system can hold, restore, repair, rerun, and create follow-up work instead of stopping at an alert.

</RichText>

<RichText id="experience-model">

## Experience Model

The interface has three levels:

1. **Changes inbox:** connected-repository PRs with operational risk and Watch Plan readiness.
2. **Watch Plan workspace:** the proposed agents, signals, triggers, guardrails, custom monitoring requirements, and unresolved mappings for one PR.
3. **Mission control and detail:** active executions sorted by urgency, with agent work, evidence, policy state, and the next permitted action.

The PR is the familiar intake surface, not the lifecycle boundary. Once a plan is armed, the Release Contract survives the PR and can generate a candidate-deployment mission, a production-promotion mission, and later feature-flag dial-up missions. This preserves deployment-console scanability while preventing the product from becoming a transcript or a GitHub review clone.

</RichText>

<RichText id="ux-principles">

### UX Principles

- Use a quiet, operational shell: compact sidebar, restrained status color, dense tables, predictable detail panels.
- Make Watch Plan state visible in the PR list: `Not required`, `Draft`, `Needs input`, `Ready`, or `Armed`.
- Compile freeform monitoring requests into visible structured clauses; never execute an opaque prompt as production policy.
- Explain why each agent and signal was selected: organization policy, changed code path, dependency, historical incident, or developer request.
- Require all unknown metric mappings and unsupported actions to be resolved before a plan can be armed.
- Lead with the release outcome and customer impact before the agent's narrative.
- Use status chips only for finite states; use text and numbers for evidence.
- Keep agent activity collapsible. The default view shows a summary, latest action, elapsed time, and verdict.
- Open tool inputs, outputs, logs, and artifacts on demand in a drawer or evidence panel.
- Keep the decision bar visible at the bottom of the mission page.
- Require an approval surface that states target, blast radius, rollback target, and policy result before a production-affecting action.

</RichText>

<RichText id="runtime-separation">

### Runtime Separation

Use the AI SDK for change analysis, monitoring-prompt compilation, typed tools, specialist loops, structured outputs, and the optional mission copilot. The Watch Plan compiler produces a versioned schema; it does not store a freeform prompt as executable policy. Use Vercel Workflow for durable orchestration, waits, retries, and resumability. Persist every contract version and mission transition independently of the UI stream.

This separation is important:

- A browser refresh must not stop or erase a mission.
- Editing a Watch Plan must create a new contract version without changing already-running missions.
- A model response must not be the source of truth for action authorization.
- The mission page must be reconstructable from database events.
- A failed external call must be retryable without repeating a destructive action.

</RichText>

<RichText id="nextjs-boundaries">

### Next.js Boundaries

- Pages and layouts are Server Components by default.
- Change filters, Watch Plan editing, mission activity, dialogs, and the copilot are focused Client Components.
- Route Handlers own GitHub, Vercel, and provider webhooks because they need raw request verification.
- Server Actions own authenticated dashboard commands such as compile requirement, arm contract, rerun, approve, reject, and restore.
- Node runtime is the default because provider SDKs, database drivers, and Codex execution are server-side.
- Webhook handlers acknowledge quickly, store a normalized event, and start or signal a workflow. They do not run the full agent swarm inline.

</RichText>

<RichText id="state-machines">

### State Machines

**Release Contract:** `draft -> analyzing -> needs_input | ready -> armed -> superseded | disabled`

**Mission:** `queued -> planning -> running -> evaluating -> awaiting_approval -> passed | held | rejected | restored | failed`

**Agent run:** `queued -> running -> waiting_for_tool | waiting_for_approval -> succeeded | failed | skipped | canceled`

**Verdict:** `pass | warn | fail | unknown`

An armed contract is immutable. Editing creates a new version; already-running missions retain the exact agents, signals, thresholds, and policy snapshot they began with.

`unknown` is a first-class result. Missing telemetry, insufficient samples, unresolved metric mappings, or an unreachable provider can never silently become `pass`. A contract with unresolved items cannot enter `armed`.

</RichText>

<RichText id="policy-section">

## Policy and Action Safety

The LLM may propose agents, compile a developer's monitoring request, select experiments, explain causal chains, and propose actions. It may not silently remove policy-required coverage, treat unresolved text as a valid metric, arm a contract, or directly mutate production.

The policy engine evaluates normalized inputs:

- Organization-required agents are present for the detected change class.
- Every custom monitoring phrase resolves to a supported signal, condition, or informational note.
- The contract version is explicitly armed and matches the trigger event.
- Required agents completed.
- No critical verdict is `fail` or `unknown`.
- Measurements satisfy mission thresholds.
- Minimum sample sizes and observation windows are complete.
- Rollback or restore target exists and was verified.
- Experiment blast radius and stop conditions are present.
- Required human approval is recorded.
- The same external action has not already executed.

Every action writes an action-ledger record before calling the provider, then records the provider result. Retried workflow steps read that ledger first.

</RichText>

<RichText id="validation-plan">

## Validation

### Product Checks

- The Changes inbox makes uncovered and unresolved PRs visible without opening every row.
- A developer can understand why an agent was selected and remove only optional coverage.
- A custom monitoring request never becomes executable until every phrase is shown as a supported structured clause.
- Arming creates an immutable contract version; subsequent edits create a new version.
- The queue exposes every mission requiring a human decision without opening each row.
- A first-time viewer can identify the failed customer outcome and technical cause in under 30 seconds.
- Every agent verdict links to at least one inspectable evidence record.
- The mission can be reconstructed after refresh from persisted events.
- The decision bar never offers an action disallowed by policy.
- Agent/tool detail is accessible without turning the default page into a transcript.

### Deterministic Tests

- Watch Plan compilation for policy-required agents, code-inferred agents, and developer-requested signals.
- Unsupported or ambiguous monitoring phrases remain unresolved and block `Arm`.
- Contract-version immutability and exact snapshot retention by running missions.
- Webhook signature verification and duplicate-event handling.
- Mission correlation across GitHub PR, contract version, commit SHA, Vercel deployment ID, and PostHog flag change.
- Policy truth table for pass, fail, warn, unknown, missing rollback, and missing approval.
- Action-ledger idempotency for promote, restore, Linear, and Codex dispatch.
- Agent output schema rejection for malformed or unsupported values.
- PostHog restoration uses the exact captured prior configuration.

### End-to-End Smoke

Run one test against the demo repository:

`flawed PR -> proposed Watch Plan -> custom monitor clause -> armed contract -> Vercel candidate -> mission -> three agent verdicts -> reject -> Codex repair -> new candidate -> green rerun -> promote`

Verify the same change ID and contract version appear across the mission record, GitHub check/comment, Vercel deployment, evidence, decision, Linear issue, and repair PR.

</RichText>
